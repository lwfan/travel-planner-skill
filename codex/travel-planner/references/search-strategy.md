# Travel Search Strategy

按任务类型决定搜索顺序，不要所有问题都用同一种搜索方式处理。

## 1. 总原则

- 新建完整行程先确认必要的 brief；条件足够、前文已确认或用户授权默认后直接搜索。局部调整和单项查询只补当前任务必需的信息，格式转换仅在必要时补查，不重新发完整问卷
- 先查会直接改变路线和预算的硬信息，再补体验信息
- 优先官方和一手来源
- 地图用于动线和区域判断，不单独承担全部事实确认
- OTA 适合看价格带和可订性，不适合作为唯一事实来源
- 社区内容只补体验，不单独确认时间、票价、签证、交通规则

## 2. 查景点、门票、开放时间

适用问题：

- 某景点开不开
- 是否需要预约
- 门票多少钱
- 周一是否闭馆
- 某天是否适合安排这个点

推荐顺序：

1. 景点官网或官方公众号/官方票务页
2. 政府文旅页或官方关联平台
3. 地图服务查看营业信息、位置和用户近期反馈
4. OTA 平台补充票种、价格带和售罄情况

必须确认：

- 开放时间
- 闭馆日
- 最晚入场时间
- 是否分时预约
- 是否售当日票

输出要求：

- 用具体日期表达，例如“2026年4月13日（周一）闭馆”
- 如果营业状态来自地图或 OTA，写成“目前显示”，不要写成绝对事实

## 3. 查交通与跨城路线

适用问题：

- 机场怎么进城
- 两城之间怎么走最顺
- 火车/航班/大巴要多久
- 返程日还能不能塞景点

推荐顺序：

1. 官方交通来源：航司、机场、铁路、公交/地铁官网
2. 地图服务查看门到门耗时和换乘复杂度
3. OTA 补充价格、班次密度和备选产品

同一起终点有交通取舍时，用 `scripts/map_tools.py compare-modes` 收集地铁、打车、步行、公交的可比较结果；只查询用户允许的方式。地图返回时长与完整门到门时长分开，后者还需核实候车、上下车接驳等缺项。没有报价或步行数据就标未知，不用 0 代替；按需补查会改变用户选择的信息。

必须确认：

- 首末班时刻
- 总耗时
- 是否需要提前值机/安检/换乘缓冲
- 行李规则或站点切换成本

输出要求：

- 返程日和跨城日优先按“最保守可执行”来估算
- 当交通耗时不稳定时，优先给区间时间，不给过于精确的承诺

## 4. 查住宿区域

适用问题：

- 住哪个区更方便
- 哪一片更适合亲子/情侣/第一次去
- 要不要为了机场住远一点

推荐顺序：

1. 地图服务看景点聚类、通勤时间和机场连接
2. 酒店平台看价格带、房型供给和取消政策
3. 社区内容补充安全感、夜间氛围、饮食便利度

重点判断：

- 去核心景点是否顺路
- 去机场/车站是否折腾
- 是否值得为了便宜牺牲大量通勤时间
- 同行人是否适合夜生活区、老城区、住宅区或景区边

输出要求：

- 给推荐区域时，要写“适合什么人”和“为什么不推荐另一个常见区域”

## 5. 查天气、季节、节假日

适用问题：

- 这几天冷不冷
- 是否会下雨
- 适不适合户外
- 有没有假期客流或特殊活动影响

推荐顺序：

1. 天气服务
2. 政府或官方节假日安排
3. 景点公告或活动页

必须确认：

- 具体日期天气
- 温差
- 降雨概率或极端天气提醒
- 节假日是否影响开放时间和客流

输出要求：

- 明确到具体日期
- 天气只作为辅助，不要把预报当成绝对结果
- 如遇不稳定天气，默认给雨天替代项

## 6. 查签证、入境、支付准备

适用问题：

- 是否要签证
- 能否免签/过境
- 需要准备什么材料
- 当地支付和电话卡怎么弄

推荐顺序：

1. 使领馆、移民局、官方入境页面
2. 航司或机场官方说明
3. 支付/通信官方产品页面
4. 社区内容补充实际体验

必须确认：

- 证件要求
- 停留时长规则
- 是否支持过境免签或电子签
- 资料要求和生效日期

输出要求：

- 引用时写清楚适用国籍和日期
- 不确定用户国籍时，先问清楚再回答

## 7. 查活动、展览、演出

适用问题：

- 当地最近有什么活动
- 某个展值不值得去
- 某天晚上有什么可安排

推荐顺序：

1. 官方活动页、场馆官网
2. 官方票务或合作票务页
3. 地图与内容平台补充口碑和周边动线

必须确认：

- 举办日期
- 场次时间
- 票价
- 售罄风险

输出要求：

- 把活动当作“可插拔模块”，不要让整个行程过度依赖单一活动

## 8. 查餐厅、本地体验和顺路小点

适用问题：

- 吃什么、住哪里附近吃饭方便
- 某区域有哪些高分餐厅、咖啡、夜市、酒吧
- 每日动线附近能顺手加什么体验
- 亲子、情侣、老人是否适合某个餐厅或体验

按地区选择平台：

- 中国大陆：优先大众点评 / 美团补充餐厅口碑、排队、套餐、近期营业状态；再用地图确认距离和动线
- 中国港澳台：优先 Google Maps / OpenRice / 官方页面，按城市实际常用平台补充
- 海外：优先 Google Maps 看位置、评分、近期评论、照片、营业状态和预约链接；再用官网、官方社媒、Tripadvisor 或当地平台交叉确认

判断规则：

- 不只看总评分，要看近期评论、差评原因、照片是否真实、是否适合同行人
- 餐厅推荐必须服务当天动线，不要为了网红店让用户大幅绕路
- 如果推荐“必吃”，要说明为什么值得专程；否则默认写成“顺路可选”
- 对营业时间、预约、临时歇业不要只信内容社区，至少用地图或官方渠道二次确认

接入边界：

- 如果当前环境没有 Google Maps / 大众点评插件或 API，就用普通网页搜索、地图网页、用户提供链接或浏览器检索作为替代
- 大众点评和部分地图平台可能有登录、反爬和区域限制，不承诺全自动抓取
- 可以先把平台作为“搜索优先级”和“证据来源”接入；需要稳定自动化时，再单独配置 API、浏览器或第三方搜索服务

输出要求：

- 每天最多推荐 2-4 个顺路餐饮/体验点，避免把行程变成餐厅清单
- 标注“专程值得去 / 顺路可选 / 备选”
- 海外餐厅尽量给英文名或当地语言名，方便用户在 Google Maps 搜
- 国内餐厅尽量给商圈/分店名，避免同名店混淆

## 9. 失败与降级策略

如果一轮搜索后仍然不够确定，按下面方式降级：

- 不强行给唯一答案，改成 2-3 个稳妥选项
- 对低置信度信息加“建议以官方最新信息为准”
- 先给路线框架，再把待确认项单列出来
- 对关键阻塞信息直接回问用户，不要靠猜测补完
