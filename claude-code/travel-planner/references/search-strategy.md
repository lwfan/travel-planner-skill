# Travel Search Strategy

按任务类型决定搜索顺序，不要所有问题都用同一种搜索方式处理。

## 1. 总原则

- 先确认 brief，再搜索
- 先查会直接改变路线和预算的硬信息，再补体验信息
- 优先官方和一手来源
- 地图用于动线和区域判断，不单独承担全部事实确认
- OTA 适合看价格带和可订性，不适合作为唯一事实来源
- 社区内容只补体验，不单独确认时间、票价、签证、交通规则

## 2. 查景点、门票、开放时间

适用问题：

- 某景点开不开
- 是否需要预约
- 门票多少钱
- 周一是否闭馆
- 某天是否适合安排这个点

推荐顺序：

1. 景点官网或官方公众号/官方票务页
2. 政府文旅页或官方关联平台
3. 地图服务查看营业信息、位置和用户近期反馈
4. OTA 平台补充票种、价格带和售罄情况

必须确认：

- 开放时间
- 闭馆日
- 最晚入场时间
- 是否分时预约
- 是否售当日票

输出要求：

- 用具体日期表达，例如“2026年4月13日（周一）闭馆”
- 如果营业状态来自地图或 OTA，写成“目前显示”，不要写成绝对事实

## 3. 查交通与跨城路线

适用问题：

- 机场怎么进城
- 两城之间怎么走最顺
- 火车/航班/大巴要多久
- 返程日还能不能塞景点

推荐顺序：

1. 官方交通来源：航司、机场、铁路、公交/地铁官网
2. 地图服务查看门到门耗时和换乘复杂度
3. OTA 补充价格、班次密度和备选产品

必须确认：

- 首末班时刻
- 总耗时
- 是否需要提前值机/安检/换乘缓冲
- 行李规则或站点切换成本

输出要求：

- 返程日和跨城日优先按“最保守可执行”来估算
- 当交通耗时不稳定时，优先给区间时间，不给过于精确的承诺

## 4. 查住宿区域

适用问题：

- 住哪个区更方便
- 哪一片更适合亲子/情侣/第一次去
- 要不要为了机场住远一点

推荐顺序：

1. 地图服务看景点聚类、通勤时间和机场连接
2. 酒店平台看价格带、房型供给和取消政策
3. 社区内容补充安全感、夜间氛围、饮食便利度

重点判断：

- 去核心景点是否顺路
- 去机场/车站是否折腾
- 是否值得为了便宜牺牲大量通勤时间
- 同行人是否适合夜生活区、老城区、住宅区或景区边

输出要求：

- 给推荐区域时，要写“适合什么人”和“为什么不推荐另一个常见区域”

## 5. 查天气、季节、节假日

适用问题：

- 这几天冷不冷
- 是否会下雨
- 适不适合户外
- 有没有假期客流或特殊活动影响

推荐顺序：

1. 天气服务
2. 政府或官方节假日安排
3. 景点公告或活动页

必须确认：

- 具体日期天气
- 温差
- 降雨概率或极端天气提醒
- 节假日是否影响开放时间和客流

输出要求：

- 明确到具体日期
- 天气只作为辅助，不要把预报当成绝对结果
- 如遇不稳定天气，默认给雨天替代项

## 6. 查签证、入境、支付准备

适用问题：

- 是否要签证
- 能否免签/过境
- 需要准备什么材料
- 当地支付和电话卡怎么弄

推荐顺序：

1. 使领馆、移民局、官方入境页面
2. 航司或机场官方说明
3. 支付/通信官方产品页面
4. 社区内容补充实际体验

必须确认：

- 证件要求
- 停留时长规则
- 是否支持过境免签或电子签
- 资料要求和生效日期

输出要求：

- 引用时写清楚适用国籍和日期
- 不确定用户国籍时，先问清楚再回答

## 7. 查活动、展览、演出

适用问题：

- 当地最近有什么活动
- 某个展值不值得去
- 某天晚上有什么可安排

推荐顺序：

1. 官方活动页、场馆官网
2. 官方票务或合作票务页
3. 地图与内容平台补充口碑和周边动线

必须确认：

- 举办日期
- 场次时间
- 票价
- 售罄风险

输出要求：

- 把活动当作“可插拔模块”，不要让整个行程过度依赖单一活动

## 8. 失败与降级策略

如果一轮搜索后仍然不够确定，按下面方式降级：

- 不强行给唯一答案，改成 2-3 个稳妥选项
- 对低置信度信息加“建议以官方最新信息为准”
- 先给路线框架，再把待确认项单列出来
- 对关键阻塞信息直接回问用户，不要靠猜测补完
