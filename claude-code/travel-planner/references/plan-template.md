# Travel Plan Template

按需选用下面的结构，不必全部输出。

## 1. Pre-Plan Questions

仅在新建完整行程且关键偏好未明确、用户尚未授权默认时，先发精简问卷并等确认。只问尚缺且会改变方案的信息；已确认、条件足够或明确授权默认时，列明条件后直接继续。局部调整、单项查询和格式转换不重新发整份问卷。

建议固定成这种结构：

- 我目前已知：
- 我还需要你确认：
- 你回复完这些后，我再开始搜索和规划：

问卷内容：

- 出发地和想去哪里？
- 具体日期或玩几天？
- 几个人去？[独行] / 情侣 / 朋友 / 亲子 / 带老人？
- 预算大概在哪个档位？经济 / [中等] / 舒适 / 度假型？
- 这次最想要什么：[经典路线] / 美食 / 拍照 / 放松 / 亲子 / 性价比 / 少折腾？
- 节奏想轻松一点还是高密度一点？松弛 / [均衡] / 高强度？
- 有什么必须去 / 不想去 / 不能接受的点？可在这里补充地铁、打车、步行、公交偏好和步行量限制。
- 输出形式：[纯文字] / 带图 HTML / 一图流 / 文档版？

方括号 `[]` 表示默认档位。根据目的地和用户已知信息调整默认项，但必须让清单里的默认项与后面“按默认档位继续”的说明一致。

输出形式固定使用 `[纯文字] / 带图 HTML / 一图流 / 文档版`。不要把“表格版”“带预算清单”列为输出形式；预算清单、交通建议和预订清单是行程内容，默认应该包含。

可以提供默认档位供用户选择，用户明确允许后即可采用并直接继续，不再次请求确认：

- 如果你暂时不想细说，我可以先按“第一次去、经典路线、节奏均衡、中等预算、纯文字版”做一版；想看更美观的版本也可以直接说“带图 HTML”或“一图流”

## 4. Option Comparison

目的地未定时可对比 2-4 个目的地；路线或玩法未定时，通常比较 2-3 个确有差异的版本。全部候选遵守用户硬约束，并采用相同日期、人数和费用口径：

| 方案 | 路线 / 体验差异 | 预算区间 | 移动与步行负担 | 适合谁 | 主要代价 |
| --- | --- | --- | --- | --- | --- |
| 主推荐（可切换） | 按实际方案填写 | 标币种、人均或总额及含费范围 | 按已知信息填写 | 与用户偏好关联 | 明确取舍 |
| 可选方案 | 写出真正不同之处 | 同口径比较 | 同口径比较 | 什么偏好下更合适 | 明确取舍 |

其他可比较维度：

- 季节和天气
- 预算级别
- 往返耗时
- 城市内移动难度
- 亲子 / 老人 / 情侣 / 独行适配度
- 是否需要提前抢票

明确要求详细行程时，直接展开主推荐，并附其他版本的差异摘要，不等待用户先选。探索阶段可先给框架供选择。用户已指定方案或要求按推荐继续时直接推进。始终区分“我推荐的版本”和“用户确认的版本”。

## 5. Day-by-Day Skeleton

每一天尽量包含：

- 区域 / 城市
- 上午锚点
- 下午锚点
- 晚间安排
- 用餐建议
- 交通方式与预计耗时
- 雨天或体力不足时的替代项

对机场接送、带行李、赶时间或交通取舍明显的路段，可附交通比较；普通短途不机械展开四种方式：

| 方案 / 实际交通组成 | 预计耗时及范围 | 费用及口径 | 步行量 | 换乘 | 主要取舍 |
| --- | --- | --- | --- | --- | --- |
| 主推荐 | 地图估时或已核实区间 | 已知票价 / 估算 / 未知 | 已知值或待核实 | 已知值或待核实 | 推荐原因 |
| 可选方案 | 同起终点比较 | 与主推荐同口径 | 同口径 | 同口径 | 什么情况下值得切换 |

按需保留 2-3 个确有区别的可行选项；用户明确要全部方式则全列。来源缺失不能填 0；打车注明候车时间和车费是否已计入；不可行或待核实项单独说明，不当成满足硬约束的推荐。
